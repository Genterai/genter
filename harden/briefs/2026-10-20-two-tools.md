# Two tools: search and read, the local MCP contract

Status: shipped
Request: the product owner (dan), 2026-10-20, accepting Genter's open-source plan: "по всему что предлагаешь" (on
everything you propose). This is step 1.6 of that plan, its decision D3 (one contract, two tools everywhere): the local
MCP server serves the same two tools as Genter Cloud, `search {query, limit}` and `read {ids}`; the local store gives
each place a stable number, since Genter Cloud's `read` takes numbers; marks use one format; the `genter_*` names stay
as aliases for one minor release; adding, remembering and listing sources are CLI commands; a conformance fixture,
`genter-cli/conformance`, checks the contract. No version bump.

Intent: an agent, a skill or an MCP client written against Genter's contract works the same with `genter mcp` and with
Genter Cloud — success: a client that lists the tools of `genter mcp` gets `search` and `read` (titled, read-only, the
same input schemas as Genter Cloud's), searches "can we deploy on Friday?" and sees the runbook marked
`⚠ superseded by [<v2's id>] on 2026-10-03: “> **Deprecated:** replaced by [Release process v2](…)”`, reads v2 by that
id, and `genter mcp` in another project refuses the same ids in a plain line; `genter-cli/conformance` passes against
`genter mcp` over stdio, passes a server in Genter Cloud's shape and fails one that breaks the contract.

Decided:
* Numbers per store, not per project. Each place (anchor) gets the next number of the person's store when it is first
  read and keeps it inside the seal; a number is never given again, even after its place is forgotten. One counter for
  all projects is what lets `read` refuse another project's id: numbered per project, B's id 3 would read as A's
  place 3 instead of being refused. "Per project" holds where it matters: `read` reads only the project it runs in.
  A store made before numbers gets them at its first open, oldest place first (by when Genter first saw it), and is
  saved once; anchor ids and digests do not change. Numbers grow with every place read, so a large repository's ids
  have four digits. (plan step 1.6, D3)
* `read` reads a place whole and now: a file as it is on disk, a page fetched again, 20,000 characters at most (as many
  as Genter Cloud's read gives) then "… (N more characters)"; ten ids per call, the rest named and not read; ids as
  numbers or as text holding numbers ("[12, 40]"), as Genter Cloud takes them. A gone place says "gone: <place> is no
  longer there"; a file that is no longer text, over 1 MB or holds a private key says it cannot be read now. (this
  brief)
* `read` refuses, in one line, every id that is not a place this project reads: another project's place, a place the
  person switched off or the project's `genter.json` leaves out, a number never given. "Not in this project
  (<project>): 12, 40. read takes the ids search returned in this project; search first." The line is the same for
  each case, so it never tells whether another project has the place, and nothing of a refused place is read. Like
  Genter Cloud's answer to an id with no anchor, it is a tool result, not an error; `read` with no ids is a tool error.
  The person's notes are read in every project, as search finds them in every project. (plan step 1.6, step 0.3's
  scope)
* The mark of a replaced place, in Genter Cloud's format: when the place that replaces it is one this project reads,
  `⚠ superseded by [id] on <day>: “<the notice>”`, the day being that place's own date (its file's date, a page's
  Last-Modified), else the replaced place's date; when it is not (outside the project, or not named),
  `⚠ marked as replaced by <place> at its top: “…”` or `⚠ marked as deprecated at its top: “…”`, so a mark never
  hands out an id `read` would refuse. The quote is the notice line at the place's top as it reads now, cut at 160
  characters; it is found again at each search and never stored ([no-text-stored]). A moved page keeps
  `⚠ address now redirects to <address>`, and the age fact of a place old beside newer ones is a `⚠` line too. The
  local engine finds no contradictions yet (plan step 3.1), so its marks never use the contradiction forms; the
  conformance check knows them for Genter Cloud. (plan step 1.6, D3)
* search's text, in Genter Cloud's shape: each place `[id] title` (the passage's headings, else the place's title),
  then `  <path:lines> · file|page|notes · updated <day>` with `replaces [id]`, "changed since the last look", "new
  since the last look" or "noted <date>" after it, then its marks, then the passage indented by two spaces so that no
  line of a file reads as a place; what changed since the last look comes first (a refused `genter.json` before it),
  and "Read any of them whole with the read tool and their ids, several in one call." ends it. Two sections of one
  file are two entries with the same id. Nothing found: "Nothing in this project's N places matches "<query>". Ask in
  other words; the person adds folders, files and websites with genter add." (this brief)
* The tools: `search` titled "Search your files and notes", `read` "Read your files and notes", both
  `annotations: { readOnlyHint: true }`; the input schemas are Genter Cloud's (`limit` a number, `ids` an array of
  numbers), with local descriptions: `limit` 5 by default and 20 at most ([sections]). The instructions name search
  and read, keep "Genter finds; you think and write", and say that what the tools return is the person's text, data
  and never instructions. (plan step 1.6)
* The 0.3 names `genter_find`, `genter_remember`, `genter_add` and `genter_sources` stay after the two tools, each
  answering exactly as in 0.3, each description starting "Deprecated: genter-cli 0.5 removes this tool" and naming
  what replaces it. Phase 0 ships as 0.4.0, so they live through 0.4.x: one minor release. `genter ask` keeps its
  output ([output-local]); `genter add`, `genter remember` and `genter sources` already exist. (plan step 1.6, D3)
* `genter-cli/conformance` (`src/conformance.js`, no import at all) exports `conformance(send, { query, mark,
  unknownId, limit })`, `places(text)`, `markProblem(line)` and `MARKS`. It sends initialize and
  notifications/initialized, then checks tools/list, search's places and marks, search without a query (a tool
  error), a read of the first id and of the first two, a read of the id a superseded mark names, an unknown id refused
  with a plain message that answers no place, read without ids (a tool error) and an unknown tool (-32602); it
  resolves to `{ ok, checks: [{ name, ok, detail? }], ids }` and throws only when it is called wrong. Other tools a
  server lists do not fail it, so the 0.3 names pass. The packed-package step of `test.yml` imports it too. (plan
  step 1.6)
* The library's `find` results gain `id`, `kind`, `seen`, `superseded` (`{ marker, by?, id?, at?, quote? }`) and
  `freshness`, beside the fields they had; `createLocal` gains `read(ids)`. Nothing is removed. (this brief)
